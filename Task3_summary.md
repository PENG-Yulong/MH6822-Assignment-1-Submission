# Task 3 — One-Page Design Summary

## JurisLens: What It Is and Why It Was Built This Way

**The problem it solves.** A bank like Standard Chartered that lends to customers in both the United States and Singapore faces two different sets of rules for how to govern its credit-scoring AI models. These rules are not just different in detail, they reflect genuinely different political choices. The US under the current administration has deprioritised enforcement of algorithmic fairness and exempted generative AI from model risk requirements. Singapore has moved in the opposite direction, requiring board-level accountability, SHAP-based explanations in denial letters, and governance of all AI including GenAI. A bank that thinks passing US regulatory examination means it also passes Singapore examination is wrong. A bank that uses a single-jurisdiction compliance tool to manage both is flying blind in one of them.

**What the tool does.** JurisLens takes a trained credit model and runs it through the relevant compliance checks for a specified jurisdiction. Run it with jurisdiction = US, and it applies the four-fifths disparate impact rule, generates Regulation B 2026 adverse action notices with up to four principal reasons (no SHAP required), and produces a US examination checklist. Run it with jurisdiction = SG, and it applies the MAS FEAT dual metric (demographic parity plus equal opportunity, both within 5 percentage points), generates adverse action notices that include SHAP factor rankings and a human-review right, and requires board approval evidence before declaring examination readiness. The same model. The same data. Different outputs.

**The central design choice.** Every parameter that differs between jurisdictions is stored in a versioned configuration file ('jurisdiction\_config.py'), annotated with the regulatory instrument it derives from and the date it took effect. This is not a UX preference, it means that a compliance officer can go back to any historical assessment and know exactly which rules were active at the time. Most competing tools store regulatory rules as flat configuration files that are not versioned, meaning you cannot answer the question "what rules was this denial notice generated under?" when an examiner asks three years later.

**What it doesn't do and why.** The tool does not provide a regulatory checkbox completion tracker, even though several competitors offer this. We believe a checkbox dashboard trains compliance officers to optimise for documentation rather than genuine risk reduction. The tool does not automatically retrain models when it detects drift that decision requires human judgement about model design and data quality, and we do not want to be a system that outsources that judgement to an algorithm. The tool does not cover the EU AI Act, not because it is unimportant, but because it is still being operationalised and the compliance cycle is long enough that a v0.1 would be making guesses rather than encoding law.

**What we would add with more time.** Conditional SHAP stability monitoring: tracking whether SHAP feature importance rankings are consistent across income quartiles, not just in aggregate. This would catch a model that behaves erratically for low-income applicants while appearing stable overall, which is a fair lending risk that aggregate metrics miss. We would also add a regulatory change alert system tied to official instrument publications, so that when OCC issues a new bulletin or MAS updates its guidance, the configuration reviewer is notified automatically rather than relying on someone remembering to check.
